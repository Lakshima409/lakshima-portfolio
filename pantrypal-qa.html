Software Quality Assurance – PantryPal Testing Case Study

Manual Testing | Test Case Design | Defect Investigation | API Testing | Regression Testing

Project overview

PantryPal is a full-stack recipe recommendation and meal-planning application. This case study documents quality assurance work performed on the existing application without modifying its functionality, except for the documented BUG-001 fix.

Technologies involved: React, Node.js, Express.js, Flask, MySQL, Python, scikit-learn and REST APIs. QA activities focused on validating application behaviour, API inputs, pantry functionality, data validation and application workflows. Not every feature or service was fully tested; limitations are stated transparently.

QA objectives

  • Validate functional behaviour.
  • Identify input validation issues.
  • Verify API responses.
  • Test positive and negative scenarios.
  • Check database-related behaviour where accessible.
  • Identify and document defects.
  • Perform retesting and regression testing.
  • Maintain structured QA documentation.

Software Testing Life Cycle (STLC)

  1. Requirement Analysis
  2. Test Planning
  3. Test Case Development
  4. Test Environment Preparation
  5. Test Execution
  6. Defect Reporting
  7. Retesting and Regression Testing
  8. Test Closure

Requirements were reverse-engineered from source code, routes, controllers and schema. No formal client requirements, stakeholder interviews or production testing took place.

Test planning and test case design

44 test cases were designed across 9 modules, using positive, negative and boundary-value techniques.

  • Authentication and authorisation: TC-AUTH-001..008
  • Pantry item creation: TC-PANTRY-001, TC-PANTRY-002
  • Pantry item updates: TC-PANTRY-003..005
  • Quantity validation: TC-PANTRY-002, TC-PANTRY-004
  • Recipe recommendation: TC-RECIPE-005
  • API request validation: TC-API-001..003
  • Database validation: TC-DB-001..003
  • Error handling: invalid recipe id, weak password, missing fields

BUG-001 details

Original input: quantity "500 g".

Initial API result: HTTP 400 "Quantity must be a number."

Root cause: Mismatch between validation middleware and controller parsing.

Fix: Validation aligned with supported quantity formats.

Post-fix API result: HTTP 201, quantity 500, unit g.

Evidence: Original failure preserved; successful post-fix retest; automated Node.js regression suite 261/261 passed. Manual retesting and automated regression testing are separate activities.

Defect investigation and resolution – BUG-001

Issue: Pantry quantity validation rejected valid quantity strings such as "500 g".

Root cause: The validation middleware rejected non-numeric strings before the request reached the controller's existing parseQuantity function.

Investigation: inspected the pantry API route, traced validation middleware, reviewed controller parsing logic, reproduced the issue through the API, identified the mismatch between validation and controller behaviour.

Fix: aligned validation with supported quantity formats, added regression tests, preserved existing invalid-input and negative-value restrictions.

Verification: original failing test result preserved; post-fix retest passed; API reproduction returned HTTP 201; automated Node.js test suite 261/261 passed.

Detection→ Investigation→ Root Cause→ Fix→ Retesting→ Regression Verification

This does not imply that all possible PantryPal defects have been resolved.

Additional QA findings

QA-FINDING-001 – Quantity boundary inconsistency

Create accepts extremely large quantities; update rejects values above 1,000,000. The intended business limit remains unconfirmed.

QA-FINDING-002 – Empty quantity behaviour

Empty, null and missing quantities pass validation; the controller converts these values to zero. The intended API contract requires clarification.

These are additional findings requiring product decisions, not confirmed resolved defects.

API testing

Practical API testing was performed using PowerShell Invoke-RestMethod against the live Node server. Postman was only explored/learned, not used as a completed practical testing tool.

Example reproduction:

POST /api/pantry
{"name":"Flour","quantity":"500 g"}

After the fix, the request returned HTTP 201 with quantity 500 and unit g. No JWT tokens, credentials, secrets or private data are exposed.

Database testing

SQL validation used read-only SELECT statements. Integrity checks on existing tables passed. Limitations: meal-plan tests blocked because required diet-plan tables were missing; shopping-list tests blocked because shopping_list_items.completed was missing; ratings tests blocked because the ratings table was missing. These features were not fully validated.

Retesting and regression testing

The original BUG-001 failure was reproduced, investigated, fixed and retested. Initial result: FAIL. Post-fix retest: PASS. Automated regression suite: 261/261 passed. No retesting of unrelated defects that did not occur is claimed.

Testing limitations

  • Only 24 of 44 designed manual test cases were executed.
  • Migration-dependent features remain untested.
  • Docker testing was not performed.
  • SMTP email delivery was not tested.
  • Flask AI services were not started for relevant testing.
  • Performance, WCAG and mobile testing were outside the executed scope.
